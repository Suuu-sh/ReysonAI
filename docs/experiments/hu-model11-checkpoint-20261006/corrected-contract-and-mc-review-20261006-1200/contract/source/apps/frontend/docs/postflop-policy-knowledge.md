# ポストフロップAI方針づくりのナレッジ

方針（`.local/postflop-ai/{slug}-policy.json` / `-later-policy.json`）を新しく作る・作り直す・直すときに最初に読む。
これまでの改善で分かったことを1か所にまとめたもの。詳細の正本は各リンク先。新しい発見は末尾に日付つきで追記する。

**2026-10-06・今回の新HU検証:** 先に1試行の高速化と旧モデルとの比較を報告し、その後に代表12フロップ × 評価ボット3種 × 両席 × 各10,000試行へ戻す。バランス監査は全1,755正規化フロップを維持し、ターン／リバーは既存の形 × 高さの区分から固定シードで選ぶ100フロップに限る。後半は**全ボードではない**。これは旧仕様の「全1,755フロップで後半も監査」からの明示的な仕様変更。定義・固定一覧・証跡要件は [HU検証契約v1](specs/hu-validation-stratified-later-v1.md) を正本とする。ここでいう後半100ボードはターン／リバーの起点となる100フロップで、各4ターン × 各3リバーの従来サンプリングは維持する。

関連: [postflop-ai-pilot.md](postflop-ai-pilot.md)（対応経路・実行順）、[postflop-defence.md](postflop-defence.md)（防御計算の正本）、
[postflop-explanation-lessons.md](postflop-explanation-lessons.md)（説明文・レンジ表の教訓）。

## 1. 前提（決定済み）

- AI推定であり GTO・ソルバー出力ではない。表示も「AI生成ソリューション」の枠組み。
- **ポストフロップEVはプロダクトに出さない（2026-10-01）。** 個別ハンドEV（`hand-ev` / `later-hand-ev`）は研究用で、今回の方針検証では実行不要。別工程のオフラインMonte Carlo比較と範囲を明示したfixed-seed照合は必要であり、これを省略する意味ではない。
- フロップ基礎データ（flop-base）は新規生成しない。その場計算で足りる。
- 従来の対象はヘッズアップ44局面（SRP 11、3betポット15、4betポット15、SBリンプ3）。今回の新HUはマルチウェイのプリフロップ経路から2人になる別カタログ407局面で、旧結果と検証契約を混同しない。フロップ以降も3人以上が残るマルチウェイは別作業。
- 外部ベンチマークはプリフロップのオープン5つだけ（GTO Wizard 合計頻度 ±3pt）。ポストフロップは自前の監査で判断する。

## 2. 方針が決めるもの・計算が決めるもの

- **AIが書く**: ベット/チェック頻度とサイズ配分、レイズの割合。フロップは `policy.mjs`、ターン/リバーは `later-policy.mjs` のルール（node × line × texture × tier）。
- **計算が決める（方針で書いても上書きされる）**:
  - コール/フォールド: 相手の到達レンジ・カード除去・必要勝率（レーキ込み）・実現率から `defence.mjs` が計算する。
  - リバーとオールインのブラフ比率の上限（bluff cap）。
  - リバーのオールインは SPR で制限（shove/pot > 2.5 なら bet125 に移す）。
  - 防御の下限（MDF − 10pt を割らないよう最強のフォールド手からコール）。
- 再レイズ（`*_vs_raise2..`）は方針に書かせない。基準配分（`policy.mjs` の `RAISE_REFERENCE`）を使う。

## 3. 作り直しの手順

今回の新HUでは、次の順序を優先する。旧45件の保存物と、旧契約で受け入れた新HU5件の既存証跡は元のスコープ・バイト列で保ち、新契約へ自動昇格しない。

1. 1試行の高速化を先に行い、同条件の旧モデルとの差、変更前後の時間・メモリ、重い処理、数値一致の確認範囲を一度報告する。64試行などの短い確認はsanity／回帰確認であり、720,000試行の代わりではない。報告前に大量計算を開始しない。
2. ソース・方針・到達レンジ・シードを固定し、代表12フロップ × 3ボット（standard/passive/aggressive）× 2席 × 各10,000試行、計720,000組の比較の正式証跡を揃える。独立した整合性照合・明示した範囲の照合を行う。fresh720,000件の全量再計算は自動追加しない。旧audit --allの全量fresh replay合格とは区別する。モデル11のstrict/compositeの区別、completion証明とunresolvedの扱いは従来の契約を保持する。
3. フロップのバランス監査は全1,755クラス。後半は固定した100フロップのみで、各4ターン × 各3リバー。各局面の実到達レンジで到達不能を別計上し、到達不能や不都合な結果を理由にサンプルを差し替えない。
4. 新契約・選択manifest・ソースと方針の識別子で結果とチェックポイントを結び付け、警告・未解決・未評価を報告する。既存のエラー判定、警告しきい値と解釈、独立レビューは変えない。既存の全量証跡はソース・方針・入力・ボードの完全一致を検証できた範囲で参照できるが、新規実行と数えない。最適化ソースへの再利用には厳密な数値一致とidentity再結合の証明が必要。旧64試行は10,000試行条件を満たさない。全量実行前には新契約の実装・検証が必要で、この文書と100ボード一覧だけでは実行済み・受入済みにならない。

以下は従来HUの作り直し手順。今回の新HUへ旧全ストリート実行器や旧証跡をそのまま適用しない。

1. プリフロップのレンジを変えたら、**到達レンジが変わった局面の方針は全部古くなる**（入力の fingerprint が一致しなくなる）。`postflop-ai:audit --all` で "AI policy source is stale" を確認する。
   - BB がコールする SRP のように方針の入力が変わらない局面は "Candidate or simulation report is stale" になり、`simulate` だけやり直せばよい。
2. 古い方針は消さず `.stale-YYYYMMDD.json` などに改名して退避する（既存候補は自動上書きされない）。
3. `generate` → `generate-later` → `simulate` → `audit` の順に局面ごとに実行。
4. 実行はリソース上限と保存先の排他を守り、最後の監査は独立した保存先で行う。並行実行中の「Saved simulation report differs from fixed-seed replay」は書込み競合と決めつけず、入力・方針・実行ソース・保存物を確認する。再実行の成功だけで以前の不一致を受入根拠にしない。
5. 最後に `node --test tests/*.test.mjs`（`postflop-browser-compute` は古い方針ファイルがあると落ちる）。

### 生成モデル

- 既定は Codex（`--model gpt-6-luna` など、ChatGPT サブスクリプション）。
- **Codex が上限のときは `--model claude-sonnet-5-5`**。`claude-` で始まるモデルは `runClaude`（`claude -p`、ツールなし）で生成する（2026-10-02 追加、44局面をこれで生成済み）。
- 過去の従来HUでは数分／局面、4並列の44局面で約1〜2時間だったが、今回の新HUモデルの所要時間へ流用しない。高速化の実測と実際の検証範囲を基に見積もる。

## 4. 指示文（プロンプト）で効いたルール

`generate.mjs` の `promptFor` / `promptForLater` に入っている。変えるときはこの意図を残す。

- JSON のみを返させる。根拠文・コード・余分なプロパティを禁止する（検証で落ちる）。
- 各 node × tier に `line='any', texture='any'` のフォールバックを必須にする。overrides は node あたり最大20。
- `*_first` ノードには line 別（aggressor / defender / checked）と texture 別（flush / pair でスローダウン、ブランク・オーバーカードでバレル、チェックスルー後はプローブ）の上書きを最低3つずつ。
- OOP と IP を別に書かせる（OOP はチェック多め・リードは少なめ。`oop_first` を `ip_first` にコピーしない）。
- ドンクベットは少なく: ターン/リバーの `*_oop_first` で line='defender'（前のストリートで相手のベットにコールした）のルールを全 tier に書かせ、ベット合計を monster 約20%・strong/draw 約15%・medium/air 5%以下にする（2026-10-03 追加）。
- リバーのブラフ比率をサイズに比例させる（ベットする手のうち air が 33%→約20%、75%→30%、125%→36%、オールイン→40%）。
- レイズには必ずブラフかドローを混ぜる（強い手だけにしない）。
- 「相手は固定ボットではない。降りすぎる相手を搾取しない」と明記する。
- 相手の伏せ札を推測させない。レンジはストリートごとに行動に応じて狭まる、とだけ伝える。

## 5. 監査の警告の読み方と対応

`audit` は PASS/FAILED（整合性）と「Advisory EV warnings」（止めない警告）を出す。

| 警告 | 意味 | 対応 |
|---|---|---|
| `overcall` | 強い手以外が、MDF を満たすのに必要な分より15pt以上多く守っている | オールインへの応答（`*_vs_allin`）なら `node scripts/postflop-ai/fix-overcall.mjs <spot>` で機械的に絞る（悪化しない場合だけ採用）。フロップの `ip_vs_33` などはコールを `defence.mjs` が計算しているので方針では直らない。実現率表や防御モデルの問題として扱う |
| `overfold` | MDF より15pt以上少なくしか守っていない | まず防御下限（MDF−10）が効いているか確認。方針側のベットがブラフ不足なら作り直し |
| `value-only-raise` | レイズの中身がほぼ強い手だけ | フロップ・ターン1回目なら指示文/方針を直す。`*_vs_raise2..` は基準配分の問題 → `RAISE_REFERENCE` を直す（2026-10-02 にドロー/air の再レイズを少し追加） |
| `bluff-ratio`（リバー、under） | 小さいベットの air が目標より少ない | **構造的に全方針で出る**。リバーまで air 判定で残る手が少なく、方針で air のベットを90%に上げても air 比率は数%しか動かない（2026-10-03 確認）。防御計算のブラフは勝率基準なので、実害は防御側の overfold で見る。参考扱い |
| `bluff-ratio`（over） | ブラフが多すぎる | bluff cap がリバー/オールインでは上限をかけるが、方針自体も直す |

## 6. 過去の失敗と教訓

- **固定の継続頻度は使えない**: 初版は tier ごとの固定コール/フォールドで、ベットサイズや相手の構成を無視していた。→ コール/フォールドは計算に置き換え（`defence.mjs`）。
- **リバーのオールインが広すぎた**: ~17倍ポットのシャブに対しトップペアが55%コールし、トップペアでのシャブが不当に高EVに見えた。→ オールインへのコールしすぎを `overcall` で検出、リバーのオールインは SPR で制限。
- **実現率に EQR 平均を使って失敗**: ハンドEVから出した EQR は「コールで実現する勝率の割合」とは別物で、BB が 75% ベットに MDF 57% のところ 9〜23% しか守らなくなった。→ tier × ポジションの明示的な実現率表を使う（`defence_realization`）。
- **方針がブラフ不足だと防御が降りすぎる**: 最適応答は方針の偏りをそのまま読むので、搾取されうる降りすぎになる。→ 防御下限（MDF − 10pt）。
- **再レイズのノードが未カバー**: 繰り返しレイズ（最大4回）を入れた後、`balance.mjs` が `*_vs_raise2..` を読めず全局面の監査が止まった。→ 方針に書かれていない再レイズは基準配分で補う（`laterPolicyMix` と同じ扱い）。
- **スタック不足でコール扱いになったレイズの後の手順**: 実際には起きない手順をハンドEVが辿ってエラーになった。→ その手順は到達不能として飛ばす。
- **プリフロップの自動補完の段差がそのまま到達レンジに乗る**: コールが期待値しきい値で急に100%になる段差（例: 33 は100%、22 は0%）があると、ポストフロップの到達レンジも歪む。プリフロップを直してから方針を作る。

## 7. 作ったあとに確認すること

1. 今回の新HUは第3節と[HU検証契約v1](specs/hu-validation-stratified-later-v1.md)に従い、代表Monte Carlo／範囲を明示した独立照合、全1,755フロップ監査、固定100フロップ起点の後半監査を別々に確認する。後半の結果に「全ボードではない」と明記し、固定シード・100件一覧・区分ごとの母数と抽出数・到達不能・警告・未解決件数を添える。未抽出1,655フロップの後半をclean／PASSに数えない。旧`audit-all-boards.mjs`は既定`--street all`であり、フロップのみの点検時間と全ストリート点検を同一視しない。「フロップのみ約30秒／局面」は旧測定で、今回の所要時間の根拠にしない。
2. 警告の種類と件数を前回と比べる（2026-10-02: 44局面で計616件 → 再レイズ基準配分にブラフを足して508件。残りの大半はリバーの under bluff-ratio と、計算防御によるフロップの overcall）。
3. 代表ボードで画面を開き、ベット頻度・サイズの分け方が極端でないか（同じ tier が全部同じサイズ、OOP が IP と同じ、など）を目で見る。
4. 説明文の確認は [postflop-explanation-lessons.md](postflop-explanation-lessons.md) のチェックリストに従う。
