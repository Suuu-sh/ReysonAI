# Offline-evidence MDF promotion veto: non-production candidate

Status: design and isolated helper under development; no model identity or runtime integration has changed. No candidate certificate is approved for application.

The helper operates after the unchanged legacy calculation. It receives the exact post-cap/pre-floor mix and the final legacy mix, then only returns the added call mass to fold. Raw calls, raises and the legacy floor/ceiling decision remain intact. No threshold is recomputed, no other hand gets replacement promotion and an MDF shortfall is allowed. Nothing imports this helper into the product or the legacy defence implementation.

A trusted replay must construct a binding containing the spot, exact board/hero, complete first-bet history, chip geometry, current numerical model, intervention version, saved support and both policy hashes/bytes. The six legacy saved-input JSON files also have explicit raw-byte records, beyond semantic seat-row support. Source identities separately cover the complete base runtime graph, inherited fallback implementation, classifier and reach semantics. Exact compatible opponent support is hashed as well. There is no rank cutoff or suit-isomorphic expansion.

Certificate proofs additionally bind the raw research report, fixed-sample protocol and sampling implementation. Unknown, incomplete, inconclusive, changed-model or mismatched contexts return the original legacy mix without applying the veto. Actual candidate application requires a separately supplied trusted review receipt binding the complete certificate content, current context and exact candidate implementation SHA-256 plus the complete live binding-builder dependency closure. A certificate cannot approve itself; edits to its proof or the candidate source invalidate the receipt. No real receipt is being created by the author. The explicit preview entry point remains visibly unapproved and is usable only for counterfactual research. The historical review of the seven diagnostics does not itself approve this implementation.

The eventual runtime must obtain identities from its compiled/validated build and current data, rather than trusting request-supplied hash strings. The present Node-only helper is not a product API, signature verifier or deployment implementation. Any accepted integration needs a new model identity, derived-artifact invalidation and a distinct reviewed delivery contract.

Completed as an unapproved research prototype: the binding/certificate builder; known-distribution and game-payoff contracts; mismatch/no-refill/no-ceiling tests. Pending: all affected-combo comparison; the eight preregistered continuation controls; independent code review and delivery acceptance. Original policy and raw research evidence remain unchanged.

## Scope and statistical qualifications

The eight added cases spend a separate nominal 0.01 family budget from the original seven. Combining both families yields at most a nominal 0.02 union bound under the IID Monte Carlo model, not 0.01. The current helper validates a single certificate's family allocation; it does not implement a candidate-wide bundle budget. Any combined approval manifest must explicitly account for both protocols before making a candidate-wide claim.

Research harness v2 extracts tested sampler/moment helpers and corrects the raw diagnostic boundary to apply any root raise cap first. Uncapped KQ parity is only an uncapped-case check; cap-active roots have a genuine diagnostic correction and require their own contract. The original v1 source and evidence are untouched. No reclassification or legacy runtime decision change is part of this harness correction.


The candidate accepts only the model's six-decimal frequency representation, requires exact integer-micropercent conservation for the promotion, and separately requires the raw and legacy JavaScript Number totals to be identical. Near-tolerance mass discrepancies are rejected rather than silently normalized. Fractional raises and partial promotion are explicit contract fixtures.


The full builder closure now includes `build-flop-promotion-veto.mjs`, `flop-promotion-veto.mjs`, `audit-identity.mjs` and `rollout-diagnostic-contract.mjs`, discovered transitively instead of relying on a builder-file hash alone. Dedicated tests mutate each dependency in an isolated copy. Builder tests also use altered copies of real reports/protocols, validate an actual pinned binding, reject source changes and show that whitespace-only saved-input changes cannot reuse an old certificate.

The 2026-10-04 short validation passed all 27 contracts with no skips, an exact 128-sample uncapped-root v1/v2 parity check, and seven frozen-report binding replays. Four negative examples remove only the floor-added call in the explicit preview; three controls remain unchanged. Every actual candidate result remains unapplied without a trusted review receipt. The successful sequential run took 5.785 seconds with a cumulative child-process RSS high-water mark of 147,580 KiB. An earlier assertion incorrectly required the Welford mean to equal integer 1 exactly instead of accepting the observed binary64 value 0.9999999999999999; the assertion was corrected to a 1e-14 tolerance without changing the numerical algorithm. Both run logs are retained. Exact tested source identities and results are recorded in `low-flop-overcall.contracts.json`.

An offline substitution into the 48 archived facing-node tables changes only four of 21,546 node/combo rows. The aggregate call-frequency reductions are 0.1103, 0.1182, 0.1194 and 0.8733 percentage points in the respective affected nodes; all other rows retain their archived mix. See `low-flop-overcall.veto-table-preview.json`. This narrow exact-context candidate therefore does not resolve general overcalling. The check reuses the already executed preview outputs; it is not a fresh integrated runtime audit of every combo, nor authority to extend the exceptions to other suits or boards.


Research-data-dependent cache/builder tests are explicitly skipped in ordinary fresh checkouts lacking the pinned fixture; they never synthesize a reference strategy. The research validation command sets `REQUIRE_LOW_FLOP_RESEARCH=1`, turning missing fixtures into a hard failure, so its result cannot silently pass through skips. `LOW_FLOP_RESEARCH_ROOT` may select an already restored fixture. The prototype cannot be accepted for delivery until its pinned fixture transfer/storage and dedicated mandatory research gate are established; an ordinary application test run with these tests skipped is not evidence of candidate validation.
