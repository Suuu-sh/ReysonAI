  1. 途中で、後ろからさらにコール・レイズが入る流れ（今は「その他の席は全員フォールド」に固定）。
  2. コーラー3〜4人の流れ。
- さらに、段階1・2のデータは画面（レンジ画面のアクション履歴）からまだ一部しか辿れない。これも対象。

## 1. 作るもの（優先順）

### 1a. 画面から段階1・2のデータを辿れるようにする（データは変えない）
- `src/estimated/RangeWorkspace.tsx` / `src/estimated/action-path.ts` のアクション履歴で、段階1・2で保存した全ての判断を選んで進めるようにする。対象は、コーラー2人以上、スクイーズ後の 4bet / 5bet、コールド4bet後の続き。
- 各判断で、関係する全員のレンジ表を並べて出す（既存の決まり：「参加している全員のレンジ表を同期して横に並べる」）。
- データが無い流れは「データなし」と表示する。ほかの局面のレンジで代用しない。
- 段階2のデータは大きいので、必要な分だけ読み込む（既存の遅延読み込みに揃える）。

### 1b. 後ろからさらに入ってくる流れ
- 対象：スクイーズ・コールド3bet・コールド4bet の後、まだ行動していない席がコール（オーバーコール）またはさらにレイズする流れ。
- 範囲は「1人目のコール・レイズが入った後は、残りの席は全員フォールド」までに区切る。区切った前提は AGENTS.md に1行書く。
- 応答する席・アクション・サイズは、既存の規則（`sizing_rules.py`、`configs/multiway-preflop-stage2.json`）に揃える。新しいサイズが必要なら設定ファイルに足し、ヘッズアップ用の設定（`configs/cash-6max-100bb.json`）は変えない（ポストフロップ方針の照合値が変わるため）。

### 1c. コーラー3〜4人の流れ
- オープン → 3人・4人がコール → 後ろの席の応答（コール / スクイーズ / フォールド）と、スクイーズへの応答。
- 到達頻度が極端に低い流れ（例：全員の頻度の積が 0.01% 未満）は作らず、「データなし」として一覧に残す。

## 2. 守ること

- 既存データ（ヘッズアップ、リンプ、段階1・2、相手像）の頻度は1行も変えない。
- レンジは generator で手札グループごとの頻度を明示して作り、`npm run build:estimates` / pipeline で出す。JSON を直接編集しない。
- 大きな生成物は、段階2と同じ持ち方（Git LFS のアーカイブ＋検証用のハッシュ）にする。リポジトリに展開済みの大きな JSON を入れない。
- 監査：止めるべき違反0。警告は件数と代表例を報告。
- 外部のソルバー値は使わない。
