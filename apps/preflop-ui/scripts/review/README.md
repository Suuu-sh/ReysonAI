# 別モデルによるレンジレビュー

生成したモデル（現在はGPT）とは**別ベンダーのモデル**（Claude・Geminiなど）に、同じ局面を独立して審査させる仕組み。
同じモデルに自分の出力を見直させると同じ癖で同じ誤りを見逃すため、レビュアーは生成元と異なるモデルにする。

## 流れ

```text
build-packets.mjs → .local/review/packets/<spot>.{blind,critique}.json   （レビュアーに渡す資料）
                  → .local/review/answer-key/<spot>.json                  （カナリアの正解。レビュアーには渡さない）
各モデルで実行   → .local/review/results/<model>/<spot>.{blind,critique}.json
score-reviews.mjs → .local/review/report.md                                （一致度・カナリア検出率・合意した指摘）
```

採用するのは「2つ以上のレビュアーが同じ方向の修正を提案し、修正後も `npm run build:estimates` の検証を通るもの」だけ。
1モデルだけの指摘や検証を通らない修正は、人が判断する保留リストに回す。

## 2つの審査モード

| モード | レビュアーに見せるもの | 目的 |
|---|---|---|
| blind（独立推定） | 局面・サイズ・計算済みの数値だけ。**現在の頻度は見せない** | 先入観なしの頻度と比べ、大きく食い違うハンドを見つける |
| critique（批評） | 現在の頻度・理由・数値・検証指標 | 具体的な誤りと修正案を、根拠の数値付きで出させる |

blind は1局面30ハンドを層別に抽出する（強いハンド、アクションの境界、ブラフ候補、明確なフォールド）。
全169ハンドを毎回独立推定するより安く、食い違いが出やすい所に集中できる。

## カナリア（レビュアー自体の検査）

critique の資料には、わざと壊した行を2つ混ぜる（例：強いペアをフォールド100%にする、弱いオフスートを3bet 100%にする）。
正解は answer-key にだけ保存する。カナリアを見逃すモデルの指摘は信頼度を下げる。
モデルごとの検出率を記録すれば、どのモデルをレビュアーに使うべきかを数字で選べる。

## 審査の観点（プロンプトに含める）

1. 合法性：頻度の合計100、合法なアクションのみ、到達不能ハンドの扱い
2. 数値との整合：必要勝率・勝率・相手の降りる率と、コール／レイズ／フォールドの選択が矛盾しないか
3. ポジション：OOP/IPや後ろに残る人数を反映しているか
4. レンジ構成：バリューとブラフの比率、ブロッカーの使い方、強いハンドが降りすぎていないか
5. 前後の局面との整合：前の局面で選ばれたハンドだけが到達しているか
6. 理由文の正確さ：理由が頻度と数値に一致しているか

## 出力形式

- blind：`{ spot_id, reviewer_model, hands: [{ hand, mix: {action: percent}, confidence, rationale }] }`
- critique：`{ spot_id, reviewer_model, overall: { score, summary }, issues: [{ hand, severity, category, proposed_mix, rationale, cited_facts }] }`

`proposed_mix` と `mix` のキーは、その局面の合法アクション（例：`three_bet` / `call` / `fold`）。

## 外部参考値（合計頻度のみ）

`.local/benchmarks/<spot_id>.json`（git管理外）に、外部ソルバーのその場面の**アクションごとの合計頻度**だけを記録する（ユーザー提供のスクリーンショットから手入力）。
- `npm run benchmark` で保存データとの差を一覧にする。目安は ±3pt。
- 審査資料には `reference_frequencies` として載る。レビュアーは「合計がずれている場合、どのハンド群で埋める／削るのが自前の勝率・監査と整合するか」を提案する。ハンド単位でチャートに寄せることはしない。
- 条件（レーキ、サイズ）が保存データと違う場合は、その差を考慮して判断する。
